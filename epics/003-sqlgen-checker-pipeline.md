# Epic 003: SQL Generator, Checker and Deterministic Pipeline

**Status:** Not started
**Goal:** Turn a hand-written `ChangeSet` into a checked, reversible SQLite migration inside a real project folder, with no LLM involved. The tester drives it with `nocodo-api init` and `nocodo-api changes`, then the reviewer reads the project folder.

**Prerequisite:** Epic 002.

---

## Context

- This epic builds the determinism core (`PRD.md` §6 "Determinism"). Epic 004 plugs the Schema agent into the same pipeline, so the checker has to be trustworthy before any LLM output reaches it.
- Migrations are written but **not applied** to `data.sqlite`; applying is epic 006. The checker still runs every pending migration on a throwaway DB, so each new migration is tested on top of all earlier ones.
- Dependency direction (see `AGENTS.md`): `orchestrator → types, sqlgen, checker`. `api` only parses arguments and calls the orchestrator.

## Tasks

### Task 1: `nocodo-sqlgen` (pure, no I/O)

- `apply(spec: &SchemaSpec, changes: &[SchemaChange]) -> Result<SchemaSpec, ApplyError>`. It fails on unknown or duplicate tables and columns, and on a rename to an existing name. `ApplyError` is a typed enum.
- `generate(before: &SchemaSpec, change_set: &ChangeSet) -> Result<Migration, ApplyError>`, where `Migration { up: String, down: String }`. SQL is generated from the change list, not from a diff, so renames stay renames.
- Conventions that every `CREATE TABLE` gets:
  - `id INTEGER PRIMARY KEY`, plus `created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))` and the same for `updated_at`.
  - Column type mapping:

    | `ColumnType` | SQLite |
    |---|---|
    | `Text`, `Date`, `DateTime` | `TEXT` |
    | `Integer`, `Money` | `INTEGER` |
    | `Boolean` | `INTEGER` with `CHECK (col IN (0, 1))` |

  - `references` → `REFERENCES <table>(id)`.
  - `unique` columns and unique indexes are emitted as `CREATE UNIQUE INDEX`, never as inline `UNIQUE`, so `AddColumn` with `unique` works too.
  - Index names are derived: `idx_<table>_<col1>_<col2>` or `uidx_…`.
- Per change:
  - Native `ALTER TABLE` for `AddColumn`, `RenameTable`, `RenameColumn`, `DropTable` and `AddIndex`.
  - A **table rebuild** for `AddForeignKey` and `DropColumn`, using SQLite's 12-step procedure (https://sqlite.org/lang_altertable.html#otheralter): create `<t>_new`, copy rows, drop, rename, then recreate indexes.
- `down.sql` restores the *structure* of `before`, applying inverse steps in reverse order. Dropped columns and tables come back empty; that is expected and documented in the generated file's header comment.
- Every generated file:
  - begins with `-- Generated by nocodo-sqlgen from change set "<name>". Do not edit.`, with no timestamps or versions, so output is byte-stable;
  - wraps its body in `PRAGMA foreign_keys = OFF; BEGIN; … COMMIT; PRAGMA foreign_keys = ON;`.
- The migration folder also gets `metadata.toml` containing `run_in_transaction = false`. Diesel can't change `foreign_keys` inside its own transaction, so the SQL manages its own. See `~/Projects/diesel/diesel_migrations/src/file_based_migrations.rs`.
- Snapshot tests with `insta` cover the up and down SQL of every `SchemaChange` variant. The snapshots are the main review material for SQL.

### Task 2: `nocodo-checker`

Two layers. Both return `Vec<Finding>` (`nocodo_types::Finding`), each with a stable snake_case `code`.

**Static rules** (`check_change_set(current: &SchemaSpec, cs: &ChangeSet, confirm_destructive: bool)`):

| Code | Rule |
|---|---|
| `empty_change_set` | `changes` is empty |
| `invalid_name` | Table, column or change-set name isn't `^[a-z][a-z0-9_]{0,62}$`, starts with `sqlite_`, or is an SQLite keyword (embed the full list from sqlite.org/lang_keywords.html) |
| `reserved_column` | A user column is named `id`, `created_at` or `updated_at` |
| `missing_description` | A table or column description is empty |
| `unknown_table` / `unknown_column` / `duplicate_name` | Mapped from `sqlgen::ApplyError` |
| `bad_reference` | `references` names a missing table, or `AddForeignKey` targets a column that isn't `Integer` |
| `added_column_not_nullable` | `AddColumn` on an existing table with `nullable: false` (existing rows would have no value) |
| `destructive_not_confirmed` | The change set is destructive and `confirm_destructive` is false |

Messages say what's wrong and what to do instead. Epic 004 feeds them back to the LLM.

**Dry run** (`dry_run(db: Option<&Path>, migrations_dir: &Path, new: &NamedMigration, after: &SchemaSpec)`):

1. In a temp dir (`tempfile`), copy `data.sqlite` if one exists, otherwise create an empty DB. Copy `migrations/` and add the new migration.
2. Run all pending migrations with `FileBasedMigrations::from_path` and `MigrationHarness`, stopping just before the new migration.
3. Introspect the DB and compare it with the spec it should match. Code `db_does_not_match_spec`: this catches drift from earlier migrations.
4. Run the new migration and compare with `after`. Then:
   - run `PRAGMA foreign_key_check` (code `foreign_key_violation`);
   - revert it and compare with the earlier snapshot (code `not_reversible`);
   - run it again and compare with `after` once more.
5. Any SQL error → `sql_error` with the SQLite message.

- Introspection uses `PRAGMA table_list`, `table_info`, `foreign_key_list`, `index_list` and `index_info`, normalized and sorted. The expected shape is derived from a `SchemaSpec` using sqlgen's type mapping.
- Ignore `__diesel_schema_migrations` and `sqlite_*` tables.
- Dependencies:
  - `diesel` with the `sqlite` feature;
  - `diesel_migrations`;
  - `libsqlite3-sys` with `bundled`, at the version Diesel 2.3 accepts, so prebuilt binaries don't depend on the system SQLite;
  - `tempfile`.

  Record any Cranelift problem in the `AGENTS.md` override table.

### Task 3: `nocodo-orchestrator`: project folder and pipeline

- `Project::init(dir, name) -> Result<Project>`:
  - fails if `dir` exists and isn't empty;
  - creates `project.json`, `specs/schema.json` (empty spec), `migrations/`, `inputs/`, and `events.jsonl` with one `ProjectCreated` event (actor `System`).
- `Project::open(dir)`: reads `project.json`.
- Event log: `append(actor, kind) -> Event`, which assigns `seq` and `at`, and `events() -> Vec<Event>`. Append-only, one JSON object per line.
- `Project::current_schema()`:
  - folds the accepted change sets from `events.jsonl` through `sqlgen::apply`;
  - errors if the result differs from `specs/schema.json` on disk, which means someone edited it by hand. The error message says so.
- `Project::propose(cs: ChangeSet, actor: Actor, confirm_destructive: bool) -> Result<Outcome>`:
  1. Append `ChangeSetProposed`.
  2. Run the static rules. If they pass, run `sqlgen::generate` and the dry run.
  3. On any finding, append `ChangeSetRejected` and return the findings. **Nothing else is written.**
  4. On success, write `migrations/<NNNN>_<name>/{up.sql,down.sql,metadata.toml}`, where `NNNN` is the next zero-padded sequence number. Write the migration folder to a temp name, then rename it.
  5. Rewrite `specs/schema.json` (pretty JSON, trailing newline) and append `ChangeSetAccepted`.
- Update the crate doc comment to match `AGENTS.md`.

### Task 4: `nocodo-api` subcommands

- Add `clap` (`derive`, `env`) and `anyhow`. Remove the version-print `main`.
- `--project <dir>` is a global option, also read from `NOCODO_PROJECT`.
- `nocodo-api init --project <dir> [--name <name>]`: the name defaults to the folder's basename.
- `nocodo-api changes --project <dir> <change-set.json> [--confirm-destructive]`:
  - prints `Accepted → migrations/0002_add_family_member` or `Rejected:` followed by one line per finding (`[code] message`);
  - exits 1 on rejection.
- The `use … as _;` lines for crates `api` doesn't call yet stay in place.

### Task 5: Fixtures for the manual session

`fixtures/change-sets/finance/`:

- `01-initial.json`: `accounts`, `people`, `categories`, and `transactions` with FKs to accounts and categories.
- `02-family-member.json`: nullable `person_id` on `transactions` referencing `people`, plus an index. This is additive.
- `03-rebuild.json`: `RenameColumn`, plus `AddForeignKey` on an existing integer column. This forces a rebuild.
- `04-drop-notes.json`: `DropColumn` on a `notes` column. This is destructive.

`fixtures/change-sets/bad/`: one file per static rule (`invalid-name.json`, `reserved-column.json`, `unknown-table.json`, `not-nullable-add.json`, …).

### Task 6: Tests

- `sqlgen`: an `apply` error test per `ApplyError` variant, plus the insta snapshots.
- `checker`: one failing test per static rule, a passing dry run for the finance sequence, and a failing dry run for a deliberately broken migration (hand-built SQL).
- `proptest` (keep it to about 64 cases): random valid change sequences on a small generated schema all pass the dry run (up → down → up matches).
- `orchestrator`, using temp dirs:
  - init, then propose the finance fixtures 01–03, then 04 rejected without confirmation and accepted with it;
  - rejection writes no files;
  - **determinism**: running the same fixtures in two fresh projects gives byte-identical `migrations/` and `specs/schema.json`;
  - hand-editing `schema.json` is detected.

## Out of scope

- Applying migrations to `data.sqlite`, backups, `inspect` (epic 006).
- Any LLM or agent code (epic 004).
- Spec diffing, i.e. generating SQL from two arbitrary specs.
- An HTTP server.

## Checkpoint

Manual session (the tester runs it, the reviewer reads `projects/finance-dev/`):

```bash
cargo run --bin nocodo-api -- init --project projects/finance-dev
for f in fixtures/change-sets/finance/0{1,2,3}-*.json; do cargo run -q --bin nocodo-api -- changes --project projects/finance-dev "$f"; done
cargo run -q --bin nocodo-api -- changes --project projects/finance-dev fixtures/change-sets/finance/04-drop-notes.json            # rejected
cargo run -q --bin nocodo-api -- changes --project projects/finance-dev fixtures/change-sets/finance/04-drop-notes.json --confirm-destructive
for f in fixtures/change-sets/bad/*.json; do cargo run -q --bin nocodo-api -- changes --project projects/finance-dev "$f"; done   # all rejected
```
